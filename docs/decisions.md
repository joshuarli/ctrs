# Decisions

Binding decisions made during execution that a later slice depends on. Campaign-level decisions live in `docs/campaign-headless-kiri.md` (Decisions section, owner/prescribed/delegated); this file records the slice-level ones with dates. Append only; never rewrite history here.

## 2026-11-13

- **Import method (CTRS-01, P1):** file-tree copy at the pin, no `.github/`, no `__pycache__`; byte-identical to upstream otherwise. Recorded in `docs/upstream.md`.
- **rustix 1.1.5 → 1.1.6 (CTRS-02, b96e7e3):** RUSTSEC-2026-0486 unsoundness in zero-length xattr queries, reachable via `kiri-image` tar unpack. Other audit findings (`glib`, `proc-macro-error`) delete with the UI in CTRS-07.
- **Musl cross-link env (CTRS-03):** the user's global cargo config injects `-B/usr/local/libexec/mold` into every target and no mold exists on this host (nor the path). musl builds must run with `CARGO_ENCODED_RUSTFLAGS=""`, which overrides all config rustflags; project `.cargo/config.toml` keeps upstream's `rust-lld` linker choice and documents the quirk. Do not "fix" by editing the global config.
- **Guest kernel build via OrbStack (CTRS-03, Decision O2):** only `cargo xtask kernel|disk` (debian:trixie, `kiri-kbuild` volumes). June 2026 owner answer: no Linux verification this run; OrbStack used solely for the kernel/disk build.

- **CTRS-09 typed config:** `crates/kiri/src/config.rs` owns the `vm.json` shape (`Resources { cpus, memory_mib }`, unknown keys ignored on load and dropped on save — exactly the settings-writer behavior; file chmod 600 on atomic save) and the `KIRI_SOCKET` resolution; `guest_dir()` lives there too (the `Resources/guest` app-bundle branch is gone). - **CTRS-09 lifecycle CLI:** `kiri start|stop|status|restart` in `service.rs`. `start` spawns the daemon with `process_group(0)` and stdio to /dev/null, waits ≤10 s for the socket, idempotent; the daemon writes `<socket_dir>/kiri.pid` (`pid start_secs`, 0600) on bind and removes it on the signal path. `status` prints pid/rss/uptime/socket (`--json`), exit 1 when not running. `stop` verifies the pid is alive and looks like a `kiri daemon` before signalling; a stale pidfile is removed, never signalled (a recycled pid is never touched). Verified end-to-end on scratch roots incl. env -i: start → status → duplicate start → stop → stale-pidfile cleanup → restart.

- **CTRS-11 firewall inventory:** `docs/firewall.md` records every nftables message the agent emits (tables `ip kiri` / `ip6 kiri`, hooks and priorities, NAT prerouting/output/postrouting, filter forward/input chains, ct-state/status helpers, per-bridge isolation rules, the atomic destroy-and-recreate batch, IPv6 NAT66, cleanup paths on bridge removal and Linux-host stop, the crash-leaves-stale-table gap, the nft_fib_ipv4 per-address fallback and the deliberate absence of nft_fib_ipv6). `agent.rs` compiled-only-on-Linux had one leftover from CTRS-07 (`running_rootfs`, dead after the FS-view removal) and `fsview.rs` had a one-argument `io::Error::new` (same class); both fixed — the musl check (`cargo check -p kiri-init --target aarch64-unknown-linux-musl`, `CARGO_ENCODED_RUSTFLAGS=""`) is now warning-free, and `cargo test --target aarch64-unknown-linux-musl --no-run` compiles the test code. The unit tests inside `firewall.rs` run for real at CTRS-13 (in-VM, root); they are not executed on macOS.
- **Typed firewall interface (CTRS-11, interface only):** `crates/kiri-init/src/linux/firewall.rs` — `FirewallPolicy → FirewallTransaction` with ownership by construction (`TableName` is the only table name; `ChainName`/`Hook` closed sets; canonical prorities 100/-100/0), explicit `Netns` on the transaction, atomic batch steps (`BeginBatch → DestroyTable → CreateTable/Chains/Rules → EndBatch`), `ApplyOutcome` with `Applied`/`RolledBack` (atomic-batch failure: the previous table survives) / `OutcomeUnknown` (ambiguous reply: re-read before rebuilding, never retry blindly), and a `FirewallBackend` trait for CTRS-12's crabtables adapter. Unused until CTRS-12; documented as such.
- **Firewall reference fixtures (CTRS-11):** `conformance/fixtures/netns-{masquerade,dnat,forward-filter,localnet,redirect}.sh` — packet-level checks of the reference semantics via `nft(8)` in network namespaces; self-contained, trap-cleaned, non-zero on failure; need Linux root; not executed on macOS; they are the CTRS-13/Gate D oracle. `conformance/fixtures/README.md` says the same.

- **crabtables adopted as an optional, pinned git dependency (CTRS-12, P7):** `crabtables` `38646b8f2f6ee7256c448849edda4459842a2e10` (laputa-systems/crabtables, the default-branch HEAD at pin time; no release tags exist; MIT OR Apache-2.0, no OpenSSL/Tokio/hyper). Feature `crabtables` in `kiri-init` selects the `crabtables_backend::CrabtablesBackend` (implements `firewall::FirewallBackend`); default stays the handwritten `netlink.rs` path. New lock packages: `crabtables`, `netlink-sys` (+ its `bytes`/`log` already present). Licenses: Apache-2.0/MIT. Build-time/binary impact: `cargo check --workspace` unchanged (~15 s); the linux/musl check adds ~30 s; guest initramfs unchanged (the adapter has no call sites until CTRS-13; `target/aarch64-unknown-linux-musl/release/kiri-init` is byte-identical with and without `--features crabtables`, sha256 `ec633abe298dfbb36abe5bdd0e7fc32803d1c91d0b1dc10583762c2c9c33a0d1`, dead-code elimination).
- **Crabtables adapter semantics (CTRS-12):** one `Batch` per table, `DESTROYTABLE` + `NEWTABLE` in the same atomic batch (matching `netlink.rs`'s destroy-and-recreate), rule `add_rule` appends (NLM_F_APPEND), chains built with the canonical type/hook/priority/policy, `Netns::File(fd)` supported via `setns` around socket creation. Error mapping: crabtables `OutcomeUnknown` → `ApplyOutcome::OutcomeUnknown` (re-read before rebuilding); every other error (batch refusal, io before send) → `RolledBack` (the atomic batch keeps the previous table). `FirewallTransaction` → `crabtables::Batch` mapping mirrors the handwritten bytes expression-for-expression (fib `addrtype`/`daddr`, `ct state/status` bitwise masks, `iifname` prefix, verdicts). Runtime equivalence (packet behavior, rejected-batch rollback, conntrack, IPv6) is CTRS-13's job, in the guest VM; nothing cuts over in this slice (P7: no cutover before Gate D).
- **`Match` atoms carry values (CTRS-12):** `DaddrV4`, `SaddrV4`, `TcpDport`/`UdpDport`, `PayloadSaddrV6 { subnet, prefix }`, `DaddrV4NotLoopback` replace the placeholder `PayloadDaddrV4 { masked_neq }`; these are the atoms the reference rules need, and the crabtables adapter consumes them directly.
- **Guest initramfs predates CTRS-11/12 (2026-11-14):** `guest/out/initramfs.cpio` and `guest/out/Image` were built before the `kiri-init` Linux-path fixes (`fsview.rs` error constructor, `agent.rs` orphan removal) and the `crabtables` feature. CTRS-13 rebuilds them (`cargo xtask guest`) before in-VM qualification runs.
