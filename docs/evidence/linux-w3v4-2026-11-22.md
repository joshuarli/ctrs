## Native tool and flush contract

Both images contain identical native **PostgreSQL/pgbench 17.12** binaries:

| Tool | SHA-256 |
| --- | --- |
| pgbench | `85babc8907723a49031277ade0749813852f3c9fe5d743cd015b38930d625235` |
| postgres | `64f09db53daa65ca5a760517963b691e5cc293df7fc711e8ae34e6450089e0a3` |

Both report `fsync=on`, `synchronous_commit=on`, `full_page_writes=on`,
`wal_sync_method=fdatasync`, `wal_level=replica`, `wal_compression=off`,
`shared_buffers=128MB`, `commit_delay=0`, `checkpoint_timeout=5min`, and
`max_wal_size=1GB`. The three durability settings are rechecked before and
after every scored trial.

The unscored trace follows real postmaster children through table writes and
CHECKPOINT. Each engine has **three successful WAL fdatasync receipts**,
including paths under `/var/lib/postgresql/data/pg_wal`. Both named-volume
data mounts resolve to host device **253:1**, ext4 `/dev/root`,
`rw,relatime`, superblock `rw,discard,errors=remount-ro`. Native PGDATA is
not inside its overlay writable layer.

Docker's mount additionally carries `master:1` propagation. The first audit
mistakenly compared propagation tokens as data-flush flags and failed after
capturing both valid receipts. That failed log is retained. The corrected
audit compares device, filesystem, data-mount flags and superblock flags from
the same immutable receipts; no trace was rerun or output relabeled.

This verifies a shared host-filesystem flush contract, not independent
physical power-loss persistence, storage-device firmware behavior or a
Mac VM disk flush contract.

## Follow-up profiles and decision

The declared throughput and latency thresholds trigger separate profiles.
Eight full-input unscored runs use ABBA order per mode. They add PostgreSQL
I/O timing and 20ms process/scheduler/I/O snapshots. A counter-control issues
an extra CHECKPOINT before read/write work to test whether preexisting
checkpoint work explains the ordering. Nothing from these runs replaces a
scored trial.

| Profile mode | Engine | RW TPS, two runs | WAL sync time, ms | WAL generated, MiB |
| --- | --- | --- | --- | --- |
| Ordinary | ctrs | 9195 / 9340 | 1299 / 1285 | 127.02 / 126.99 |
| Ordinary | Docker | 7680 / 8311 | 1145 / 1179 | 126.94 / 126.99 |
| Extra checkpoint | ctrs | 9816 / 9729 | 1161 / 1249 | 186.45 / 186.46 |
| Extra checkpoint | Docker | 9609 / 9579 | 1245 / 1320 | 186.46 / 186.45 |

The ordinary profile reverses the cohort's throughput ordering. Its WAL sync
time totals are 1.1–1.3 seconds within roughly 1.7–2.2 second profiled execs.
Those totals are not an exclusive critical-path decomposition: group commit,
futex waits and background PostgreSQL work overlap. Scheduler-wait sums are
lower on native in these ordinary profiles, not evidence of native starvation.

The extra CHECKPOINT control changes full-page-image work: about 187 MiB of
WAL instead of 127 MiB. It therefore cannot isolate a pure checkpoint-delay
effect or be substituted for the fixed contract. It does not reproduce a
native deficit either. The leading background-checkpoint explanation is
**not established**. No claim attributes the original loss specifically to
device latency, cgroup policy or sampler asymmetry.

Both pgbench and the database run in the same container and communicate by
its local Unix socket. Actual traces show direct PostgreSQL host syscalls,
not a ctrs forwarding, VM or storage-RPC path. The verified data path and the
reversed profiled ordering do not support an engine change. No hypothesis
is manufactured merely to consume the three-attempt limit. The cohort's
RW-throughput loss and slower restart stay visible and unresolved; neither
is promoted into parity or erased by the profiles.
