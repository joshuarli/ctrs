Paired AB/BA cohorts, 10 pairs per cell, on `joshs-MacBook-Pro.local`
(Apple Silicon, arm64). Every trial passed its exact-output checks
(W12 receipts; W13 byte-exact receivers and capacity controls). Source
`ee5c829`; ctrs binary `d9465bc2…`, initramfs `f3ab7344…`; OrbStack
29.8.2. Lanes are reported separately: **D** is installed defaults
(ctrs 2 vCPUs, OrbStack 9); **M** gives ctrs OrbStack's vCPU count and
memory. Ratios are ctrs/OrbStack paired medians with 95 % bootstrap CIs;
below 1 favours ctrs, and throughput is inverted so the same reading
holds. These are comparative measurements on this host. They are not

### Diagnosis

- Every path that crosses the VM boundary lands at 0.5–0.7 GB/s in either
  direction. Four streams are no faster than one, and 9 vCPUs (M lane) are
  no faster than 2. The limit is one serialized path, not guest CPU count.
  Inside the guest, container↔container beats OrbStack.
- Guest CPU per GiB of published-port upload, from the
  `bench/native/diagnostics/w13_guest_cpu.py` probe
  (`w13cpu-20261118T133921`, diagnostic timings): ctrs user 0.25 s,
  system 1.15 s, softirq 0.29 s; OrbStack 0.08 / 0.30 / 0.19 s. The ctrs
  guest spends most of its cost in kernel time.
- The probe's per-thread split worked only on OrbStack. ctrs ignores
  `--pid host`: the daemon has no PidMode handling and accepts the flag
  silently.
- Draining relay sockets per wakeup without zero-fill (branch
  `perf/relay-batch`, `2263bc1`) measured 0.72 GB/s and 3.1–3.2 CPU-s/GiB
  over 3 diagnostic pairs (`base-20261118T140016-2150`). That is within
  noise of the baseline, so the user-space relay loop is not the limit.
  The branch is parked.
- These match the 2026-11-15 notes in
  [`native-performance.md`](native-performance.md) (EXP-5, host-side
  buffer widening): about 0.65–0.75 GB/s raw vsock either way, already
  window-tuned on both ends. The guest kernel posts 4 KiB vsock receive
  buffers (`VIRTIO_VSOCK_DEFAULT_RX_BUF_SIZE`, Linux 6.18.58), so
  host→guest packets carry at most 4 KiB.

### Fix: 64 KiB vsock receive buffers (guest kernel patch 0005)

`guest/kernel/patches/0005-vsock-virtio-64k-rx-buffers.patch` raises
`VIRTIO_VSOCK_DEFAULT_RX_BUF_SIZE` from 4 KiB to 64 KiB. The host binary
and initramfs are unchanged (`d9465bc2…`, `f3ab7344…`), and the kernel is
`1b2fdbc9…`. The candidate passed `conformance/smoke.sh` (21/21) and
`tests/e2e.sh` (489/489). The runs below are D-lane paired cohorts of 10
pairs on that guest:

One ctrs Mac→container trial ran at 0.61 GB/s. The other nine ran at
1.32–1.42 GB/s. Host-to-guest is no longer a deficit on a single stream.

**Buffer-size A/B and the guest→host tail.** The 10-pair guest→host
no-regression cell on 64 KiB (`base-20261118T144018-7636`, published-port
download) kept its median at 5.33 [4.82, 6.80], against 5.11 before.
However, 10 of its 30 ctrs transfers fell to 0.28–0.52 GB/s, where the
earlier minimum was 0.61. A follow-up A/B ran 5 pairs of guest→host
download per kernel (`base-20261118T152231-58ff` 4 KiB,
`base-20261118T152616-d50d` 64 KiB, `base-20261118T153005-b283` 16 KiB,
`base-20261118T153354-ca0b` 32 KiB). Every kernel showed the same tail:
one to three of 15 transfers at 0.31–0.41 GB/s, the rest at 0.55–0.71.
The tail is environmental, not the patch. During these runs a foreign
`kache-builder` container, which was not owned by this campaign and was
left untouched, ran in OrbStack with OrbStack Helper near 250 % host CPU.
OrbStack's own transfers stayed tight, so ctrs's VZ vsock path is the more
contention-sensitive one. Host→guest upload, 3 pairs each, ran at about
1.6 GB/s with 16 KiB (`base-20261118T153736-e933`) and about 2.0 GB/s with
32 KiB (`base-20261118T153938-4c20`), against 2.1–2.6 GB/s with 64 KiB, so
64 KiB stays. Cells measured from about 14:40 may include that foreign
load. The 10-pair host→guest cells above ran earlier.

Guest→host is unchanged by the patch: 0.63–0.65 GB/s published-port
download and 0.51 GB/s container→Mac upload, in 3-pair diagnostics. Its
guest packets were already 64 KiB. Four download streams total
0.675 GB/s, against 0.65 GB/s for one. Guest CPU is 0.80 s/GiB at one
stream (`w13cpu-20261118T141652`), so the guest is about half idle. The
bounded hypothesis is a Virtualization.framework vsock device ceiling on
the guest→host direction. It is not a per-connection window, guest CPU, or
the relay loop. Closing it needs a different device path.

### Mac-share request costs (kernel tracing)

A `fuse_request_send` tracepoint trace of a create+write+close loop on a
bind mount showed five serial requests per file: LOOKUP (ENOENT, 16 µs),
CREATE (85 µs), GETXATTR `security.capability` from `file_remove_privs`
(25 µs), WRITE (23 µs), and GETATTR of the parent directory for the
permission check after CREATE invalidated its attributes (20 µs). RELEASE
was synchronous on virtiofs. On the Mac itself the same loop takes
41 µs per create and 10 µs per 1 KiB write.

| Probe (µs per op) | k9 | k12 (0008 v2, 0009) | k13 (+0010, 0011) | OrbStack | Mac native |
| --- | ---: | ---: | ---: | ---: | ---: |
| open+close, read-only | 57–79 | 51 | — | 17 | — |
| open(O_CREAT) | — | 211 | 175 | 67 | 41 |
| write 1 KiB to the new file | — | 86 | 48 | 17 | 10 |
| create+write+close | 304 | 268 | 227 | 73–104 | 58 |

- 0008 v2 skips FLUSH on any close when the server lacks lock support
  and the inode has no locks. Writes already reached the server, and
  `write_inode_now` still runs for mmap'd pages.
- 0009 sends RELEASE in the background when the connection has no
  submounts.
- 0010 keeps a directory's type, mode, owner and inode number valid
  across entry changes, so no GETATTR follows a create.
- 0011 marks a just-created file without setuid or setgid `S_NOSEC`, so
  the first write skips the capability probe.

What remains per create is the LOOKUP and the CREATE round trips themselves.

On kernel k13, W12 full-bind M went from 1.38 to 1.27: install 2.08,
test discovery 2.22, and build, typecheck, warm rebuild, change and
branch switch all inconclusive (1.01–1.09). D went from 1.57 to 1.48
(install 2.03, test discovery 1.69); its build, typecheck and edit
phases (1.16–1.44) are inconclusive in the M lane, so they are the
2-vCPU default.

### W12 request mix on the Mac share (kernel tracing)

The `fuse_request_send` and `fuse_request_end` events of one traced
`npm ci` and `jest --listTests` on a bind mount, streamed from
`trace_pipe` (the guest kernel lacks hist triggers). Times are under
npm's concurrency.

| Phase, kernel | Wall s | LOOKUP (ENOENT) | WRITE | CREATE | RELEASE | GETXATTR | Directory reads |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| install, k13 | 36.7 | 310,894 (110,732) | 146,395 | 92,102 | 92,691 | 29,282 | 2,830 dirs |
| install, k14 | 34.4 | 160,666 (110,731) | 146,395 | 92,102 | 92,691 | 8 | 2,830 dirs |
| discovery, k14 | 3.1 | 4,942 (1,996) | — | — | 1,061 | — | 12,097 dirs |

Sampled stacks on k13 showed why. About 45% of LOOKUPs came from
`ctrs_fsnotify_write`. The host's FSEvents stream reports the guest's own
virtiofs writes, so each echo dropped the live dentry. The follow-up
opens and stats then looked the name up again. The refreshed attributes
cleared `S_NOSEC`, so the capability GETXATTRs returned. Patch 0012 has
FUSE stamp the inodes this guest changes. The proc file skips an event
for a cached name changed here within 2 s, for a removed name that is
already negative, and for an uncached removed name whose directory was
changed here within 2 s. A Mac edit to a file the container itself
changed within those 2 s is not raised. Test discovery is four requests
per directory (OPENDIR, READDIRPLUS, the EOF READDIR, RELEASEDIR), about
210 µs per directory on 12,097 directories.

## Bind-mount notifications (implemented)

Wire protocol 6 (`Msg::HostFsEvents`), a host FSEvents watcher over the
bind sources of running containers, and guest kernel patch 0006
(`/proc/ctrs/fsnotify`) were integrated in `2adbca0` and `a5e5ab1`. The
first integration started a thread in the guest agent, which broke every
container start: musl's set*id in raw-clone'd children fails when the
parent has other threads. A forked writer replaced the thread. Smoke
passed 21/21, and e2e passed 495/495 including the new `bind-inotify-*`
checks. Assets: binary `7184af22…`, initramfs `9a2b6c9d…`, kernel
`3c6fd926…`.

W12-watch bind, 10 pairs (`base-20261118T174235-c732`): ctrs was correct
on 101/120 in nine trials and 98/120 in one, with 0 stale, against 0/120
before. OrbStack was correct on 120/120 in nine valid trials; one failed
the harness's process-ownership check. Every ctrs miss is a five-file
burst result. Volumes miss the same results on both engines, so that is
`tsc` under native inotify, not the forwarding.

Kernel k8 (save reported as modify, ordered events), 3 pairs
(`base-20261118T212940-afee`): ctrs was correct on 97/120 in every trial,
OrbStack on 120/120, with 0 stale. The 23 misses are exactly the 23 that
both engines miss on volumes: an in-place burst edit to a file the Mac
had earlier replaced by atomic rename (`users.ts` after its atomic save,
and so on). ctrs bind therefore matches native Linux inotify; OrbStack's
bind mount does better than native. Median detection latency is 0.50 s
on ctrs against 0.66 s on OrbStack.

Event-variant A/B, 2 pairs each: k9 raises IN_ATTRIB and IN_DELETE_SELF on
the replaced inode, as a Linux unlink does (`base-20261118T220619-ab8e`).
k10 raises IN_ATTRIB and IN_MOVE_SELF and keeps the watch
(`base-20261118T215543-cd5e`). Both left ctrs at 97/120 and OrbStack at
120/120. A raw `inotifyd` probe on OrbStack shows why it differs. After a
Mac atomic replace, each later in-place append to the file arrives on
the directory watch as IN_MOVED_FROM, IN_MOVED_TO and IN_MODIFY on the
name, and `tsc` reacts to the rename pair. ctrs keeps
IN_DELETE_SELF on replaced and removed files, as on Linux.

Kernel k11 adds that rename pair: an in-place Mac modification of a
regular file is also raised on the parent as IN_MOVED_FROM and IN_MOVED_TO
of the name onto itself. On W12-watch bind, 2 pairs
(`base-20261118T234824-4ef9`), ctrs and OrbStack were both correct on
120/120 with 0 stale. This is the shipped patch 0006.

Kernel k13, 10 pairs (`base-20261119T013944-e94b`): ctrs and OrbStack
were each correct on all 1,200 results, 0 stale. Detection latency from
the Mac write to the verified output: p50 0.65 s on both, p95 1.98 s
ctrs and 2.00 s OrbStack.

## W14 connection lifecycle (D lane, 32 clients)

Functional pass, one pair per mode (`base-20261118T154226-1abf` …
`-154418-fe70`): all six modes were exact on both engines, with no leaked
sessions.

| Mode | Fixture | Run id | Result (ctrs/OrbStack paired median [CI]) |
| --- | --- | --- | --- |
| fresh (3,200 new connections) | w14-v2 | `base-20261118T155140-632e` | latency p50 5.71 [5.07, 6.73] loss, p99 0.06 [0.06, 0.96]; trial wall about 4.25 s vs 4.03 s; CPU 1.30 [1.22, 1.57] loss |
| streaming (50 chunks at 20 ms) | w14-v1 | `base-20261118T154648-a1d5` | chunk lateness p99 1.16 [1.05, 1.26] loss; CPU 1.75 loss; cleanup 0.43 win |
| reconnect (container restart) | w14-v1 | `base-20261118T154814-d69a` | reconnect p99 0.80 [0.51, 0.99] non-inferior; CPU 5.1 loss (whole restart) |

The fresh-mode p50 ratio is confounded. OrbStack drops some of the 32
concurrent connection attempts, and its p99 is about 1 s, a SYN
retransmit, in every trial. Those drops throttle its concurrency and lower
its median. ctrs admits all 32 at once and queues them in the
single-process server. On completion time ctrs is about 5 % slower, and
the clearer cost is CPU, at 1.30×. The w14-v1 fresh cohort
(`base-20261118T154501-868d`) is invalid: back-to-back trials exhausted
the Mac's 16,384 ephemeral ports (TIME_WAIT 30 s) on both engines. w14-v2
waits for free ports and classifies `EADDRNOTAVAIL` as `client_ports`. The
protective limits (`TCP_IDLE` 300 s, 1,024 TCP sessions, 64 per peer)
were not reached. An idle period above 300 s would close relayed
sessions.

## Ranked measured deficits

1. **Bind-mount change notifications: parity.** W12-watch bind went
   from 0 to 1,200 of 1,200 correct over 10 pairs on kernel k13, the
   same as OrbStack, with equal detection latency.
2. **Guest→host transfer: 5–7× slower** (container→Mac upload 0.51 vs
   3.6 GB/s; published-port download 0.63 vs 3.3 GB/s). This is a bounded
   VZ vsock device ceiling. Host→guest single-stream reached parity with
   patch 0005. Four-stream upload remains a 1.25× loss.
3. **W12 full-bind workflow: 1.48× D, 1.27× M on kernel k13.** In the M lane this is
   engine cost, concentrated in install (2.08×) and test discovery
   (2.22×) on the Mac share, where each file create costs serial host round
   trips (see Mac-share request costs).
4. **W12 all-volume workflow: 1.29× in the D lane only.** M lane parity
   (1.02): the gap is the 2-vCPU product default, an owner decision.
5. **W14 CPU per lifecycle:** fresh 1.30×, streaming 1.75× (lateness
   p99 1.16×), restart 5.1×.
6. W2 M-lane CPU per success (parked; see the W2 evidence files).

## Reproduce

```sh
cd /path/to/ctrs
export TMPDIR=$PWD/.work/tmp
python3 bench/native/runner.py baseline --a ctrs --b orbstack --pairs 10 \
  --resource-lane installed-default --case W13 \
  --transfer-path published-port --direction upload --streams 1
python3 bench/native/runner.py baseline --a ctrs --b orbstack --pairs 10 \
  --resource-lane installed-default --case W12 --workspace-layout full-bind
python3 bench/native/diagnostics/w13_guest_cpu.py
cd bench/native && python3 reporting.py --results ../../.work/native-perf/results --match <run id>
```

W12 needs `.work/tmp/kutt.tar.gz` (sha256 `862d34f4…`) and
`.work/tmp/w12-image.tar`; see `fixtures/w12/README.md`. A candidate guest
is measured by pointing `CTRS_GUEST_DIR` at its asset directory. The
runner records the hashes that the daemon boots.
