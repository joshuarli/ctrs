### Diagnosis

- Every path that crosses the VM boundary lands at 0.5–0.7 GB/s in either
  direction. Four streams are no faster than one, and 9 vCPUs (M lane) are
  no faster than 2. The limit is one serialized path, not guest CPU count.
  Inside the guest, container↔container beats OrbStack.
- Guest CPU per GiB of published-port upload, from the
  `bench/native/diagnostics/w13_guest_cpu.py` probe
  (`w13cpu-20261118T133921`, diagnostic timings): ctrs user 0.25 s,
  system 1.15 s, softirq 0.29 s; OrbStack 0.08 / 0.30 / 0.19 s. The ctrs
  guest spends most of its cost in kernel time.
- The probe's per-thread split worked only on OrbStack. ctrs ignores
  `--pid host`: the daemon has no PidMode handling and accepts the flag
  silently.
- Draining relay sockets per wakeup without zero-fill (branch
  `perf/relay-batch`, `2263bc1`) measured 0.72 GB/s and 3.1–3.2 CPU-s/GiB
  over 3 diagnostic pairs (`base-20261118T140016-2150`). That is within
  noise of the baseline, so the user-space relay loop is not the limit.
  The branch is parked.
- These match the 2026-11-15 notes in
  [`native-performance.md`](native-performance.md) (EXP-5, host-side
  buffer widening): about 0.65–0.75 GB/s raw vsock either way, already
  window-tuned on both ends. The guest kernel posts 4 KiB vsock receive
  buffers (`VIRTIO_VSOCK_DEFAULT_RX_BUF_SIZE`, Linux 6.18.58), so
  host→guest packets carry at most 4 KiB.

`VIRTIO_VSOCK_DEFAULT_RX_BUF_SIZE` from 4 KiB to 64 KiB. The host binary
and initramfs are unchanged (`d9465bc2…`, `f3ab7344…`), and the kernel is
`1b2fdbc9…`. The candidate passed `conformance/smoke.sh` (21/21) and
`tests/e2e.sh` (489/489). The runs below are D-lane paired cohorts of 10
pairs on that guest:

### Mac-share request costs (kernel tracing)

A `fuse_request_send` tracepoint trace of a create+write+close loop on a
bind mount showed five serial requests per file: LOOKUP (ENOENT, 16 µs),
CREATE (85 µs), GETXATTR `security.capability` from `file_remove_privs`
(25 µs), WRITE (23 µs), and GETATTR of the parent directory for the
permission check after CREATE invalidated its attributes (20 µs). RELEASE
was synchronous on virtiofs. On the Mac itself the same loop takes
41 µs per create and 10 µs per 1 KiB write.

| Probe (µs per op) | k9 | k12 (0008 v2, 0009) | k13 (+0010, 0011) | OrbStack | Mac native |
| --- | ---: | ---: | ---: | ---: | ---: |
| open+close, read-only | 57–79 | 51 | — | 17 | — |
| open(O_CREAT) | — | 211 | 175 | 67 | 41 |
| write 1 KiB to the new file | — | 86 | 48 | 17 | 10 |
| create+write+close | 304 | 268 | 227 | 73–104 | 58 |

- 0008 v2 skips FLUSH on any close when the server lacks lock support
  and the inode has no locks. Writes already reached the server, and
  `write_inode_now` still runs for mmap'd pages.
- 0009 sends RELEASE in the background when the connection has no
  submounts.
- 0010 keeps a directory's type, mode, owner and inode number valid
  across entry changes, so no GETATTR follows a create.
- 0011 marks a just-created file without setuid or setgid `S_NOSEC`, so
  the first write skips the capability probe.

What remains per create is the LOOKUP and the CREATE round trips themselves.

On kernel k13, W12 full-bind M went from 1.38 to 1.27: install 2.08,
test discovery 2.22, and build, typecheck, warm rebuild, change and
branch switch all inconclusive (1.01–1.09). D went from 1.57 to 1.48
(install 2.03, test discovery 1.69); its build, typecheck and edit
phases (1.16–1.44) are inconclusive in the M lane, so they are the
2-vCPU default.

### Remaining install LOOKUPs on k14

A timing probe (`stat` of `/w/a/b/c/d/f` after a gap, then a missing
name twice) shows the Mac's virtiofs server grants about 1 s of entry
and attribute validity. After any gap of 0.9 s or more, one stat costs
five LOOKUPs (every path component) and a GETATTR; under 0.5 s it costs
none. The missing name costs one LOOKUP, then patch 0007's negative
cache answers.

Sampled stacks of k14 `npm ci` LOOKUPs (2,285 samples):

| Caller | Share |
| --- | ---: |
| First lookup of an uncached name (`stat`/`lstat` via `__lookup_slow`), mostly ENOENT before a create | 51% |
| Revalidating an expired dentry during a path walk (`lookup_fast`) | 41% |
| `mkdir`'s exclusive lookup | 7% |

Both causes are cacheable from facts the guest already has. A directory
this guest just made with MKDIR starts empty, and the only other writer
is the Mac, whose changes reach the guest through `/proc/ctrs/fsnotify`.
Expired directory dentries are revalidated every second although the
same notifications report Mac-side renames and deletes.

### Kernel k15: fewer LOOKUPs, same install time

Patches 0013 (a directory this guest made answers missing names without a
request for ten seconds) and 0014 (directory entries and attributes stay
valid for ten seconds) cut one traced install's LOOKUPs from 160,666 to
48,138 (ENOENT 110,731 to 32,409). e2e passes 501/501, including a new
check that the Mac's creates inside a container-made directory, a new
Mac subdirectory, and a Mac-side directory removal all show within 3 s.

The paired cohorts did not move. W12 full-bind M is 1.23 [1.19, 1.30]
(k14 1.25), install 1.92 (1.96), test discovery 2.24 (2.15); ctrs's
install is about 35 s on both kernels while OrbStack's is 17–20 s. D at
5 vCPUs is 1.28 (k14 1.26). The traced install's 34.4 s to 27.5 s drop
was confounded: the k14 trace ran at the old 2-vCPU default and the k15
trace at 5 vCPUs.

In the k15 trace every remaining request got slower as LOOKUPs went
away (WRITE mean 142 to 186 µs, CREATE 203 to 231 µs, RELEASE 180 to
225 µs). That fits a server that completes a fixed number of requests
per second regardless of how many the guest has in flight, so removing
one opcode lets the others queue longer. The patches stay: they are
correct, covered by e2e, and cut host work.

A concurrency probe confirms it (`node` workers each writing 1,500
3 KB files with `writeFileSync` into their own directory on a bind
mount; two runs per engine, files per second):

| Writers | ctrs (k15, 5 vCPUs) | OrbStack |
| ---: | ---: | ---: |
| 1 | 5,214–6,638 | 9,001–9,099 |
| 2 | 6,931–7,818 | 12,920–15,295 |
| 4 | 8,117–8,186 | 14,803–20,927 |
| 8 | 8,287–8,502 | 16,617–20,906 |

ctrs is 1.4× slower with one writer and flattens near 8,300 files/s
(about 25,000 requests/s at CREATE, WRITE, RELEASE per file), while
OrbStack keeps scaling. During the run the guest was 86% idle and the
virtiofs device has one request queue (`/sys/fs/virtiofs/*/mqs`), so
the limit is the Mac-side Virtualization.framework server, not guest
CPU. ctrs shares the Mac through one `VZVirtioFileSystemDeviceConfiguration`;
the API exposes no queue count. Further W12 install gains must remove
requests (WRITE and RELEASE are 61% of install requests on k15) or
take them off the critical path.

### Directory reads on the Mac share

A reply-size trace (`fuse_request_end` `len`, 16-byte header included)
of `readdirSync` and `ls -f` over directories of 10 to 5,000 entries
with 2- and 200-character names shows the server fills each
non-final reply to within one entry of the 16 KiB buffer (16,336–16,400
bytes) and ends every listing with a 16-byte empty reply. Skipping that
empty READDIR when a reply leaves room for a 255-byte entry would be
exact on these listings, but it would trust the server never to return
a short batch mid-listing, for example when an entry vanishes between
its readdir and stat. It saves about 12,000 of 48,000 test-discovery
requests, worth well under a second of a 120-second workflow, so it is
not worth the truncation risk and was not built.

## Bind-mount notifications (implemented)

Wire protocol 6 (`Msg::HostFsEvents`), a host FSEvents watcher over the
bind sources of running containers, and guest kernel patch 0006
(`/proc/ctrs/fsnotify`) were integrated in `2adbca0` and `a5e5ab1`. The
first integration started a thread in the guest agent, which broke every
container start: musl's set*id in raw-clone'd children fails when the
parent has other threads. A forked writer replaced the thread. Smoke
passed 21/21, and e2e passed 495/495 including the new `bind-inotify-*`
checks. Assets: binary `7184af22…`, initramfs `9a2b6c9d…`, kernel
`3c6fd926…`.

W12-watch bind, 10 pairs (`base-20261118T174235-c732`): ctrs was correct
on 101/120 in nine trials and 98/120 in one, with 0 stale, against 0/120
before. OrbStack was correct on 120/120 in nine valid trials; one failed
the harness's process-ownership check. Every ctrs miss is a five-file
burst result. Volumes miss the same results on both engines, so that is
`tsc` under native inotify, not the forwarding.

Kernel k8 (save reported as modify, ordered events), 3 pairs
(`base-20261118T212940-afee`): ctrs was correct on 97/120 in every trial,
OrbStack on 120/120, with 0 stale. The 23 misses are exactly the 23 that
both engines miss on volumes: an in-place burst edit to a file the Mac
had earlier replaced by atomic rename (`users.ts` after its atomic save,
and so on). ctrs bind therefore matches native Linux inotify; OrbStack's
bind mount does better than native. Median detection latency is 0.50 s
on ctrs against 0.66 s on OrbStack.

Event-variant A/B, 2 pairs each: k9 raises IN_ATTRIB and IN_DELETE_SELF on
the replaced inode, as a Linux unlink does (`base-20261118T220619-ab8e`).
k10 raises IN_ATTRIB and IN_MOVE_SELF and keeps the watch
(`base-20261118T215543-cd5e`). Both left ctrs at 97/120 and OrbStack at
120/120. A raw `inotifyd` probe on OrbStack shows why it differs. After a
Mac atomic replace, each later in-place append to the file arrives on
the directory watch as IN_MOVED_FROM, IN_MOVED_TO and IN_MODIFY on the
name, and `tsc` reacts to the rename pair. ctrs keeps
IN_DELETE_SELF on replaced and removed files, as on Linux.

Kernel k11 adds that rename pair: an in-place Mac modification of a
regular file is also raised on the parent as IN_MOVED_FROM and IN_MOVED_TO

## Guest→host transfer attribution (2026-11-19)

Probe: `.work/tmp/g2h/run.sh` (reproduced below), a container-to-Mac upload

| --- | --- |
| 8 GiB transfer | 15.4–17.4 s (0.49–0.56 GB/s), byte-exact |
| VZ credit window (`buf_alloc` from the host) | 262,144 bytes |
| Steady state | one 64 KiB guest packet per host CREDIT_UPDATE, every 100–150 µs |

No thread is saturated, and the guest sends only as fast as
Virtualization.framework returns credit: the vsock device carries about

the relay's socket buffers to 4 MiB changed nothing (16.2 s), and moving
the vsock interrupt off CPU 0 was within noise. Earlier records already
showed four streams no faster than one.

The VM also has a NAT NIC. A diagnostic that sends the same artifact from
a bridge container to the Mac's address on that network (192.168.64.1),
and fails unless the Mac sees the VM's NAT address as the peer, moved
4 GiB byte-exact in 2.49 s (1.72 GB/s; peer 192.168.64.51). Local Network
privacy blocks Mac processes from opening connections to the VM, not from
accepting them. OrbStack presents its host-bound connections to Mac
services as coming from 127.0.0.1, as ctrs's vsock relay does, so sending
containers straight to the NAT address would change what services see.

**Intervention (protocol 8):** after boot the daemon listens on the
Mac's NAT address and tells the agent its port and a 16-byte per-boot
token (`Msg::HostRelay`). The agent sends each `host.docker.internal`
connection there first (100 ms connect budget), with the token and the
loopback target; the daemon checks the token in constant time, relays
only to 127.0.0.1, and the Mac service sees 127.0.0.1 as before. A
connection that cannot reach the listener uses the vsock relay.

| Same probe, NAT host relay | Value |
| --- | --- |
| 8 GiB transfer | 4.49–4.74 s (1.81–1.91 GB/s), byte-exact |
| Transport (`lsof` on the daemon) | 192.168.64.51 → 192.168.64.1 in, 127.0.0.1 out |
| VZ process CPU | 7.7 s (was 11.7 s) |
| Daemon CPU | 3.0–3.2 s (unchanged) |

### W14 CPU: the agent spun on pending connects (fixed in `bf2ea2b`)

The w14-v3 streaming records put nearly all of ctrs's CPU in the VM
process (1.18–1.31 s per trial) and 54–59 ms in the daemon; OrbStack used
0.52–0.60 s in total. A guest trace of one streaming run (32 clients, 50
chunks at 20 ms, published port) had the agent on CPU 1.35 s of a 2.6 s
window and the container's server 0.20 s. Its syscalls: 512,201
`getsockopt`, 512,181 `getpeername`, 73,973 `ppoll`, 3,650 `read`.

A relay polled the host side for input while its connect to the
container was pending, but reads nothing until connected, so a client's
early bytes woke poll at once until the connect finished. The fixture's
server has Python's default accept backlog (5); 32 simultaneous clients
overflow it, the container drops SYNs, and a dropped connect resolves on
the SYN retransmit a second later, the 1 s p99 noted under fresh mode
for OrbStack too. With the fix the same run made 790 polls, the agent
used 0.046 s and the VM process 0.32 s (was 1.27 s); all 32 clients
succeeded. Regression: `relay::tests::a_pending_connect_leaves_poll_asleep_while_the_client_has_sent`
fails without the fix. Every W14 mode is re-queued on this build; any
workload whose server backlog overflows (W2, W14 fresh) also paid this.
